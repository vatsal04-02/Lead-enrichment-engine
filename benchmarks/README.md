# Benchmarks

Two kinds, **never mixed**:

| | local fixtures (`run_local.py`) | live sources (`run_live.py`) |
|---|---|---|
| content | 300 synthetic sites generated by `leadengine/fixture_sites.py` (deterministic: same ids ⇒ same content) | real company websites you list in a CSV |
| ground truth | yes — every site's published facts are known, so correctness, wrong values and invented values are measured | no — only field *presence* is reported; use `--audit N` to export a random sample for human review |
| network | localhost, fixed simulated latency (`--latency-ms`, default 40) | real |
| use | regression, tuning concurrency, capacity of the *engine* | the only valid basis for real-web success rates and cost |
| safety | fixture hosts are the only ones exempt from the SSRF address rules | refuses to run without `--confirm-permitted` and a real `LE_USER_AGENT`; robots.txt always on; ≥1 s per-domain delay |

## Run

```bash
scripts/dev_postgres.sh                                     # benchmarks use database "enrich" (tests use "enrich_test")
python -m benchmarks.run_local --sites 300 --concurrency 1,2,4,8,16,32,64 --min-delay 0.5,0
#   --latency-ms 40  --no-browser  --parse-workers N  --browser-executable PATH
python -m benchmarks.run_live --confirm-permitted --sample benchmarks/live_sample.csv --concurrency 4 --audit 25
```

Each configuration runs in its own subprocess on an emptied database; the fixture server is a separate process, so it does not
share the engine's GIL. Output: `benchmarks/results/local-<timestamp>.{json,md}`.

## Metrics (all measured; definitions)

* **companies/min** = unique input companies ÷ wall time of the worker run (duplicates excluded from the numerator;
  `input_rows_per_minute` also given).
* **latency p50/p95** = per-company `duration_ms` recorded by the pipeline (includes politeness waits and retries).
* **usable-record rate** (fixtures) = share of sites with ≥1 *correct* contact field (email/phone/address) **and** ≥1 *correct*
  identity field (company_name/description), judged against ground truth. For live runs the same rule is applied to
  *presence only* and is labelled UNVERIFIED.
* **required-field coverage** = correct values ÷ published ground-truth values for `company_name, email, phone`.
* **precision of returned values** = (returned − wrong − spurious) ÷ returned; *spurious* = a value that is not any fact the
  site publishes (the prompt-injection fixtures would show up here); *wrong* = differs from the published value.
* **duplicate rate** = in-file duplicate rows ÷ input rows (5 % seeded, with URL spelling variants); none may be enriched twice.
* **HTTP requests / AI calls per company, browser-rendering frequency, retry rate** come from `enrichment_runs` / `metrics.collect`.
* **process CPU (cores)** = CPU seconds of the engine process ÷ wall seconds (1.0 = one core saturated).
* **cost per 1,000 input / usable records**: computed only from *configured unit prices* (`LE_AI_PRICE_*`,
  `LE_COST_PER_HTTP_REQUEST_USD`, `LE_BROWSER_COST_PER_SECOND_USD`) applied to *measured* tokens/requests/seconds, so every USD
  figure is an **estimate**; infrastructure cost is excluded unless you add `compute $/hour × wall hours`. With no prices
  configured the report says so instead of printing 0 as if it were a result. Formula:
  `cost/1000 input = (Σ cost_usd_est + compute) / input_rows × 1000`; `cost/1000 usable = … / usable_records × 1000`.
  **Do not quote a cost per 1,000 records until `run_live.py` has run with real prices on a sample representative of your data.**
* **best sustainable operating point**: the smallest concurrency reaching ≥90 % of the best throughput among runs where the
  engine process stays ≤0.85 of one core and the failure rate is within 1 percentage point of the lowest-concurrency run.

## Limitations (read before trusting any number)

* Fixtures are authored by the same people who wrote the extractor; accuracy on them is a regression signal, not a real-world
  estimate. Real sites are messier (and some block bots).
* The engine, Postgres (fsync off) and the fixture process share one machine; Postgres writes are cheaper than a production
  database over a network.
* Simulated latency is a constant; real latency is long-tailed. Per-domain politeness delay dominates real throughput when each
  company needs several pages from one host — this is intentional.
* Queue/worker scaling across multiple worker *processes* is not part of these runs (single process).
